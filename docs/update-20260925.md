# Update 2026-09-25

Shipped as **v1.82.0** (minor — user-visible feature).

## Context

The café gives a visiting pastor or a first-time newcomer their whole order, food
included. The code did not: every discount class was gated on
`category === 'DRINK'`, so a newcomer who ordered a pastry was charged for it and
the offset logged understated what the café had actually given away.

Two changes were asked for together:

1. `PASTOR` and `NEWCOMER` discount FOOD as well as DRINK. `STAFF` and `PREORDER`
   stay DRINK-only.
2. The admin discount report gains a `foodBreakdown` parallel to the existing
   `drinkBreakdown`, so discounted food lines are itemised rather than only
   summed into the offset total.

Implementation and tests were done by a prior agent; this session verified,
versioned, documented and shipped them.

## Analysis

The DRINK gate existed in **two** places, not one, and that was the main risk in
the change:

- `priceLine()` — `backend/src/lib/pricing.ts:216`, submission / walk-up time
- `repriceStoredItems()` — `backend/src/lib/pricing.ts:426`, approve time

Each had its own copy of `item.category === 'DRINK'`. Widening one and not the
other would price the same order two ways depending on when the class was
applied: the customer sees one number at submission and the cashier grants a
different one at approval. Both now route through a single helper.

Two properties of how the scope is expressed are load-bearing and were checked
deliberately:

- **Allowlist, not negation.** `priceLine` coerces the category with
  `String(menu.category || '')`. A `category !== 'DRINK'` test would therefore
  treat a malformed menu record with no category as discountable and hand it out
  free. The allowlist matches nothing instead — it fails closed.
- **Exhaustive by type.** `CLASS_CATEGORIES` is a
  `Record<CustomerClass, readonly string[]>`, so adding a fifth customer class
  without deciding its categories is a compile error rather than a silent
  DRINK-only default.

`STAFF` and `PREORDER` are DRINK-only for reasons specific to each, which is why
this could not be one global "FOOD is never discounted" rule:

- `STAFF` is a flat RM5 **drink** price, not a percentage. Against food it is not
  a discount anybody decided on — it would charge RM5 for a RM6 pastry and leave
  a RM3 cookie untouched.
- `PREORDER` is the drinks-only ministry pre-order; its link already rejects food
  up front (`preorderItemRejection()`), so a food line on a pre-order is already
  an anomaly and must not be silently zeroed. It also zeroes the whole gross, so
  widening it would be uncapped cost to the café.

`celebrationApplies()` is untouched — still eligible-DRINK-only.

On the report side, `foodBreakdown` lazy-creates its per-discount-type keys
exactly as `drinkBreakdown` does, so **a discount type with no matching lines is
absent from the object rather than present as `{}`**. Both the frontend reader
and any future consumer must therefore use `breakdown[type] || {}`.

## Changes

Backend:

- `backend/src/lib/pricing.ts` — new `CLASS_CATEGORIES` allowlist (`:170`) and
  `classAppliesToCategory()` (`:185`). Both pricing gates (`:216`, `:426`) now
  call the helper instead of carrying a hardcoded `category === 'DRINK'` test.
  Header comment corrected — it had asserted "FOOD = never discounted by any rule".
- `backend/src/routes/admin.ts` — `GET /api/admin/reports/discounts` now also
  returns `foodBreakdown` alongside `drinkBreakdown`, same
  `Record<discountType, Record<itemName, quantity>>` shape. Purely **additive**:
  no existing field changed shape or meaning, so cached frontend shells holding
  the previous bundle keep working.

Frontend:

- `frontend/js/pricing.js` — display-only mirror of the same category split.
- `frontend/js/admin-dashboard.js` — reads `foodBreakdown` (via `|| {}`) and
  renders a labelled "Food" group beside "Drinks" in the existing discount
  accordion. Drink and food lines are now **labelled**: bare item names were
  unambiguous when the cell held drinks only and stopped being so. A group with
  no lines is omitted rather than shown as an empty label, and a row is
  expandable if **either** group has lines — food-only is the case the feature
  exists for. Item names go through `escapeHtml` at the new render site.
- `frontend/css/admin.css` — two rules for the new group, existing design tokens
  only, no new colours.

Tests (`backend/tests/`): `pricing.test.ts`, `admin-reports.test.ts`,
`staff-code.test.ts`, `pos-cafe-shift.test.ts`, `pos-transitions.test.ts` — new
FOOD/DRINK cases per affected class plus an approve-time reprice case, so the
second gate is covered and not just the first. Several stale comments asserting
"FOOD is never discounted" were corrected.

Docs and skills:

- `.kiro/skills/pricing-rules/SKILL.md` — category scope documented as a
  per-class fact with the one helper that owns it; the `PREORDER`
  "do not align this with the other RM0 classes" warning added; the stale
  "a newcomer who orders only food gets no reduction" example corrected.
  `description` frontmatter updated so the skill is findable on category scope.
- `.kiro/skills/invariants/SKILL.md` — the flat "FOOD is never discounted"
  invariant **withdrawn** and replaced by the per-class allowlist rule, including
  the fail-closed and exhaustiveness properties and what breaks if a report
  assumes food is always full price. `description` updated.
- `.claude/skills/{invariants,pricing-rules}/SKILL.md` — pointer stubs; only the
  `description` frontmatter changed, bodies still defer to the `.kiro` copies.
- `.kiro/skills/api-reference/SKILL.md` — the `reports/discounts` row now
  documents both breakdowns and the absent-vs-empty-key behaviour. Method, path
  and auth are unchanged.
- `docs/requirements.md` — §6 pricing table "Food Price" column corrected for
  Newcomer and Pastor (it said `Normal`, which the change makes false); the
  `Mark Newcomer` line in §4 no longer says "free drinks" only.
- `docs/feature-history.md` — v1.82.0 sprint entry; "Current Status" date;
  "Special pricing" summary line made category-explicit.

No new routes, lib modules or page modules, so the layout block in
`.kiro/steering/project.md` is unchanged. No schema, TTL or status-transition
change, so `db-schemas` and `order-lifecycle` were not touched. No new test-data
marker and no new production-writing suite, so `test-suites` was not touched.
