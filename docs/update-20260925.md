# Update 2026-09-25

Shipped as **v1.82.0** (minor — user-visible feature).

## Context

The café gives a visiting pastor or a first-time newcomer their whole order, food
included. The code did not: every discount class was gated on
`category === 'DRINK'`, so a newcomer who ordered a pastry was charged for it and
the offset logged understated what the café had actually given away.

Two changes were asked for together:

1. `PASTOR` and `NEWCOMER` discount FOOD as well as DRINK. `STAFF` and `PREORDER`
   stay DRINK-only.
2. The admin discount report gains a `foodBreakdown` parallel to the existing
   `drinkBreakdown`, so discounted food lines are itemised rather than only
   summed into the offset total.

Implementation and tests were done by a prior agent; this session verified,
versioned, documented and shipped them.

## Analysis

The DRINK gate existed in **two** places, not one, and that was the main risk in
the change:

- `priceLine()` — `backend/src/lib/pricing.ts:216`, submission / walk-up time
- `repriceStoredItems()` — `backend/src/lib/pricing.ts:426`, approve time

Each had its own copy of `item.category === 'DRINK'`. Widening one and not the
other would price the same order two ways depending on when the class was
applied: the customer sees one number at submission and the cashier grants a
different one at approval. Both now route through a single helper.

Two properties of how the scope is expressed are load-bearing and were checked
deliberately:

- **Allowlist, not negation.** `priceLine` coerces the category with
  `String(menu.category || '')`. A `category !== 'DRINK'` test would therefore
  treat a malformed menu record with no category as discountable and hand it out
  free. The allowlist matches nothing instead — it fails closed.
- **Exhaustive by type.** `CLASS_CATEGORIES` is a
  `Record<CustomerClass, readonly string[]>`, so adding a fifth customer class
  without deciding its categories is a compile error rather than a silent
  DRINK-only default.

`STAFF` and `PREORDER` are DRINK-only for reasons specific to each, which is why
this could not be one global "FOOD is never discounted" rule:

- `STAFF` is a flat RM5 **drink** price, not a percentage. Against food it is not
  a discount anybody decided on — it would charge RM5 for a RM6 pastry and leave
  a RM3 cookie untouched.
- `PREORDER` is the drinks-only ministry pre-order; its link already rejects food
  up front (`preorderItemRejection()`), so a food line on a pre-order is already
  an anomaly and must not be silently zeroed. It also zeroes the whole gross, so
  widening it would be uncapped cost to the café.

`celebrationApplies()` is untouched — still eligible-DRINK-only.

On the report side, `foodBreakdown` lazy-creates its per-discount-type keys
exactly as `drinkBreakdown` does, so **a discount type with no matching lines is
absent from the object rather than present as `{}`**. Both the frontend reader
and any future consumer must therefore use `breakdown[type] || {}`.

# Part 2 — v1.83.0: the BLESSING full-waiver discount class

Second release pass of the same day, and a **separate feature** from v1.82.0
above, though it builds directly on it. v1.82.0 made discount *category scope* a
per-class fact owned by one allowlist; this adds a fourth cashier-selectable
class that could only be a one-line allowlist entry *because* that refactor had
already landed. Two features, two versions, two changelog entries, two commits.

**Backend + frontend**, so `npm run deploy:backend` ships **first** — the POS
sends `discountType: 'BLESSING'` and the API must already accept it, or
`parseCustomerClass` narrows it to `null` and the order is approved at **full
price with no error shown**. That failure is silent on both sides, which is the
whole reason the order matters here.

## Context

STAFF, PASTOR and NEWCOMER cover the cases the café had names for. They do not
cover "we want to give this person their order" in general — a volunteer's
visiting family, someone having a hard morning, a mis-made drink remade for free.
The cashier's only options were to pick a class that was factually wrong (which
corrupts the discount report) or to collect money the café did not intend to
take. `BLESSING` gives that decision its own name and its own reported row.

## Analysis

### 1. It needed no new arithmetic, only a new name

The v1.82.0 refactor had already reduced "what does this class cost" to one
branch and "which categories does it touch" to one table. So the whole pricing
change is:

- `CustomerClass` gains `'BLESSING'` (`backend/src/lib/pricing.ts:59`)
- `CLASS_CATEGORIES.BLESSING = ['DRINK','FOOD']` (`:187`)
- `parseCustomerClass` accepts it (`:341`)

The existing `customerClass === 'STAFF' ? STAFF_DRINK_PRICE : 0` branch then puts
it at RM0, exactly as PASTOR and NEWCOMER get there. Nothing was added that could
compute a *different* number.

`DiscountType` is `Exclude<PricingRule, 'PREORDER'> | 'MINISTRY_PREORDER' |
'VOUCHER'` and `PricingRule` includes `CustomerClass` (`:73`), so the
`BLESSING` **discountType** followed from the type change rather than being
declared a second time. `summarizeOrderDiscount` writes it only when the class
actually produced a rule on some line (`:305`), so the report row is not padded
with orders that gave nothing away.

### 2. The `parseCustomerClass` question, answered on WHO DECIDES

`BLESSING` waives more than `PREORDER` does, and `PREORDER` is the one class
deliberately refused from a request body. That looks like a contradiction and is
not one: the test is **who decides**, never the size of the discount.

- `PREORDER` is assigned by the **server** from the order's stored `isPreOrder`
  flag. Accepting it from input would let anyone zero an order and have it
  reported as `MINISTRY_PREORDER` — free, with **nobody accountable**.
- `BLESSING` is chosen by a **human at the till** whose identity is written to
  `approvedBy`. The waiver has a name attached to it, and it cannot be expressed
  at all unless it can arrive in a request.

This is now written down in both `pricing-rules` and `invariants`, because the
next class added will face the same question and the wrong reading of it ("big
discounts are server-only") would either let `PREORDER` in or keep a legitimate
cashier class out.

### 3. Two surfaces, one of which needed the layout defended

The walk-up cart's selector is a list of chips — one more entry, existing
pattern, nothing to decide.

The PENDING detail modal was not. Adding a fourth button made the actions row
four `.pos-btn-lg` items, and on a 1024px counter tablet **all four fit on one
line** — putting "comp the whole order" and "reject it" a thumb-width from
"payment confirmed", the action taken hundreds of times a service. Where that row
breaks must not depend on how wide the modal happens to be, so it is forced:
`.pos-row-split` is a zero-height `flex-basis:100%` item that puts Approve alone
on the top row (it is `flex:1`, so alone it fills the width) with the three
exception actions grouped below. `.pos-reject-picker` is appended *into* that same
flex container by `showRejectDialog`, so it gained `flex-basis:100%` to keep its
own full row now that the row is fuller.

The modal button also confirms via the existing `posConfirm` helper, naming the
ringgit amount being waived. Newcomer deliberately does not confirm — choosing a
named discount is already an explicit decision — but Blessing waives the *entire*
order including food, and a mis-tap would not surface until end-of-day
reconciliation.

### 4. Pre-order cards lost both exception buttons

A pre-order is already RM0, so "Newcomer" and "Blessing" on one would only
relabel a `MINISTRY_PREORDER` as something else and muddy the report. Both are
now omitted entirely when `isPreOrder(o)`, with their listeners attached via
`?.addEventListener` so the absent nodes are not a TypeError.

### 5. Fixed enumerations: four of them, one already wrong

`discountType` is switched on against hardcoded lists in four places, and the
audit that added `BLESSING` to them found `frontend/js/reports.js` had been
**missing `MINISTRY_PREORDER`** since that type was introduced — the summary note
told the reader the discount total was made of NEWCOMER / STAFF / PASTOR /
CELEBRATION / VOUCHER while the figure above it also included ministry pre-orders.
A real, if minor, pre-existing bug, fixed in the same edit.

`admin.js` holds the list **twice** — the rendered table and the
`#btnCopyDiscounts` clipboard handler — which is how the copied summary comes to
disagree with the screen. Both now carry a comment pointing at the other.
