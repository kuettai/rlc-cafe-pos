# Update 2026-09-07

Release pass for **v1.79.0 — passkey (WebAuthn) login for the admin page.**

Nothing here was committed, pushed or deployed. See **Deploy readiness** at the
bottom for why, and what is left for the user to run.

## Context

The admin page had exactly one way in: a PIN typed on a shared counter tablet or
on a volunteer's phone. This session closes out a passkey (WebAuthn) login for
that page, so an admin can sign in with Face ID / Touch ID after enrolling a
credential once per device.

The feature was already built, reviewed and tested when this pass began. The work
here was the version bump, the changelog, documentation/skill sync, and these
notes.

**Shape of the change, and the one thing to keep in mind:** it is **purely
additive**. PIN login is untouched and remains the required fallback — there is no
migration, no forced enrolment, and an admin who never enrols sees exactly what
they saw before, apart from one extra button on the login screen.

## Analysis

### What was built

**`backend/src/lib/webauthn.ts` (NEW)** — the only place that knows the
relying-party identity:

```
RP_ID   = '153.oasisofcare.org'      // bare host, no scheme, no port
RP_NAME = 'RLC Café POS Admin'
ORIGIN  = 'https://153.oasisofcare.org'
CHALLENGE_TTL_SECONDS = 300
```

These are **constants, not env vars**, on the same reasoning that moved the VAPID
keys out of the Lambda environment: a `cdk deploy` from a shell that had not
exported them wiped the live values, and a wrong `rpID`/`origin` fails every
assertion with no useful client-side error. The module wraps
`@simplewebauthn/server` (**new dependency, v14.0.1**) so no route imports the
library directly — its option names changed shape twice across majors
(`authenticator:` → `credential:`, `registrationInfo.credentialID` →
`registrationInfo.credential.id`), so a second call site is a second thing to
migrate. It also owns the base64url helpers and the challenge
put/get/delete/expiry helpers.

Enrolment asks for a **discoverable** credential (`residentKey:'required'`), which
is what makes login usernameless: `login-options` sends `allowCredentials: []` and
the server learns the identity from the credential ID in the assertion.

**`backend/src/routes/auth.ts`** — four new routes in `handleAuth`. **No
`index.ts` change was needed**, because `path.startsWith('/api/auth')` already
dispatches there.

**`backend/src/routes/admin.ts`** — `callerFromToken()` plus two
`/api/admin/passkeys` branches (list / revoke, strictly self-service), and a fix
to a pre-existing latent bug described below.

**Frontend — `frontend/js/admin.js` and `frontend/css/admin.css` only.**
`pos.js`, `pos.html`, `config.js`, `sw.js` and `admin.html` are untouched. A
feature-detected "Sign in with Face ID / Touch ID" button on the login screen
(gated on `window.PublicKeyCredential`), a self-contained Passkeys card in
Settings (add / list / remove, independent of `btnSaveSettings`), and a shared
`applyLoginSuccess()` now used by both the PIN and passkey paths.

New CSS classes: `.admin-login-alt`, `.admin-login-or`, `.admin-login-passkey`,
`.admin-login-note`, `.admin-inert-why`, `.admin-pk-row`, `.admin-pk-empty`,
`.admin-pk-fail`.

**Challenges are prefetched so `navigator.credentials.get()/create()` are called
inside the click's own dispatch.** Safari/iOS drops user activation across an
`await`, so fetching the challenge first and *then* calling the ceremony makes the
button silently do nothing — on precisely the devices this feature exists for.

### The endpoints

| Method | Path | Auth |
|---|---|---|
| POST | `/api/auth/passkey/register-options` | JWT + ADMIN + not `forceUpdatePin` |
| POST | `/api/auth/passkey/register-verify` | JWT + ADMIN + not `forceUpdatePin` |
| POST | `/api/auth/passkey/login-options` | **public** |
| POST | `/api/auth/passkey/login-verify` | **public** |
| GET | `/api/admin/passkeys` | JWT + ADMIN |
| DELETE | `/api/admin/passkeys/{credentialId}` | JWT + ADMIN |

Full status codes and failure messages are in the `api-reference` skill. Four
details are load-bearing enough to repeat:

- **`forceUpdatePin` blocks enrolment on both register routes.** Otherwise a
  forced PIN change is sidesteppable by enrolling a credential that skips the PIN
  entirely.
- **`login-verify`'s response body is byte-identical to `POST /api/auth/login`.**
  That is a contract, not a coincidence — it is what lets one
  `applyLoginSuccess()` serve both paths. Anything added to the PIN login response
  must be added here too or the passkey path silently loses it.
- **Every `login-verify` failure is `401 {error:'Invalid credentials'}`**, with no
  exceptions: "no such credential", "bad signature" and "inactive account" are
  indistinguishable, so the endpoint cannot be used to enumerate users.
- **`DELETE` returns a JSON body, not `204`.** `admin.js`'s `api()` helper calls
  `res.json()` unconditionally, so a 204 breaks the caller. Recorded in the
  `api-reference` skill so nobody "tidies" it.

`MAX_PASSKEYS_PER_USER = 10`.

### The new record shapes

**Settings table — `PK=WEBAUTHN_CHALLENGE#{requestId}`, `SK=META`**, holding
`{challenge, userId: string|null, expiresAt}`. `expiresAt` is **epoch seconds**,
`now + 300` — deliberately the same TTL idiom `PUSH_SUB#` already uses on that
table.

**This is not a violation of the "numeric `expiresAt` only on PENDING orders"
rule.** That invariant is about the **ORDERS** table, where a stray numeric TTL
makes DynamoDB silently delete a live or archived order. Here the record is meant
to be ephemeral and TTL is the point. Worth stating explicitly because the two
look identical in a diff.

Readers still compare `expiresAt` in code (`isChallengeExpired()`) rather than
trusting DynamoDB's sweep, which is best-effort and can lag by hours. Challenges
are single-use and deleted on **every** outcome, including failed verification, so
a captured response cannot be replayed against a challenge still in the table.

**Users table — new `passkeyCredentials` attribute** on `PK=USER#{userId},
SK=META`: `[{credentialId, publicKey, counter, transports, deviceLabel,
createdAt}]`. `publicKey` is a **base64url string, deliberately not a DynamoDB
Binary attribute** — the DocumentClient would marshal a `Uint8Array` as Binary,
which round-trips back as a Buffer-ish value whose exact type depends on the SDK
version. Text keeps the record plain JSON any script or console view can read.

**Users table — `PK=PASSKEY_CRED#{credentialId}`, `SK=META`**, holding
`{userId}`. The reverse lookup that makes usernameless login possible.

### The real find: an unfiltered Scan became a data-loss bug

`PASSKEY_CRED#` is the **first non-`USER#` partition key** the users table has
ever held. `GET /api/admin/users` ran an **unfiltered `ScanCommand`** on that
table and mapped every item into the volunteer list.

Consequence: each enrolled passkey rendered as a **phantom volunteer row with a
blank name and blank role, whose Delete button carried the REAL owner's
`userId`** — so deleting the phantom deleted a live volunteer account. The
reverse-lookup record carries a `userId` attribute (that is the entire point of
the record), which is exactly why the phantom looked deletable rather than
malformed. No attacker required: an admin tidying an odd-looking row.

Fixed with `FilterExpression: 'begins_with(PK, :userPk)'`
(`backend/src/routes/admin.ts`, the `GET /admin/users` branch).

Two things make this worth recording as a general rule rather than a one-off fix:

1. **The Scan was correct when it was written** and became a defect *without being
   touched*, in a diff that did not mention it. So the rule has to be
   unconditional — every `ScanCommand` carries a `begins_with(PK, …)` filter, even
   on a table with one record type today.
2. **The test suite actively defended the defect.** A test asserted the Scan's
   `FilterExpression` was `undefined` — it had pinned "harmless today" as a
   *requirement*, so adding the filter turned the suite red and the correct fix
   looked like a regression. That test now pins the filter positively and carries
   the reason (`backend/tests/admin-users-settings.test.ts:232`).

Both are now in the `invariants` skill under a new **Single-table queries**
section, along with the corollary: adding a record type to an existing table means
grepping every reader of that table in the same change.

### Review round

1 critical + 11 risk findings.

- **The critical finding was the unfiltered Scan** above — fixed.
- Fixed in the same pass: the `forceUpdatePin` enrolment gate on both register
  routes; the wrong-user challenge check (a challenge issued to one admin must not
  enrol a passkey on another's account); a stale-token check so enrolment cannot
  **resurrect** a deleted or deactivated account; single-use challenge deletion on
  every outcome; the indexed-write `ConditionExpression` on
  `passkeyCredentials[i]` (a concurrent DELETE shifts every later index, so an
  unconditioned index write revokes the wrong passkey); the delete ordering, which
  is fail-closed on purpose (list entry first, reverse record second, so a crash
  between the two leaves an orphan pointer to an already-dead credential rather
  than a live credential nobody can resolve); the ownership condition on the
  reverse-record delete, since that key is **not** namespaced by user and an
  unconditional delete there is a cross-user write; the login blocklist applied to
  the *resolved* user, so a barred identifier does not get a second door;
  uniform `401`s on every login failure; and `publicKey`/`counter` excluded from
  the list response.
- **Deferred deliberately** — the four items under *Open items* below.

## Open items

Recorded so they are not lost. The first is a decision for the user, not a bug.

**(a) `userVerification:'preferred'` + `requireUserVerification:false` — the top
open question.** This reduces an ADMIN login to a **bare possession factor**: a
stolen *unlocked* phone signs in with no biometric and no device PIN, against a
role that can edit pricing and delete users. `'required'` is arguably the correct
setting for an admin surface. The cost of changing it later is a **re-enrolment
for everyone already registered**, so the cheapest moment to decide is before
anyone enrols. Left as-is **deliberately — this is the user's policy decision, not
the agent's.** The two values are paired on purpose: requiring at verification
what was only preferred at generation rejects legitimate authenticators, so both
move together (`backend/src/lib/webauthn.ts`).

**(b) No rate limiting on `login-options`.** It is unauthenticated and each call
writes a challenge record to the settings table. Nothing in this app has rate
limiting today, so this belongs at **API Gateway**, not bolted onto one route.
Records are small and TTL'd at 5 minutes, so the practical exposure is write cost,
not growth.

**(c) Passkeys cannot be exercised outside the production origin.**
`RP_ID`/`ORIGIN` are the single live host, so the documented local dev flow
(`npx http-server frontend -p 3001`) can **never** test this path. A
misconfiguration's only symptom is the `verify-threw` log line — which now carries
`err.message`, `rpID` and `origin` for exactly that reason. Check CloudWatch for
it if enrolment fails after deploy.

**(d) The real Face ID / Touch ID ceremony was never executed.** It needs Secure
Enclave hardware; headless Chromium rejects `navigator.credentials.get` on
`127.0.0.1` with `SecurityError`. **All browser verification used a stubbed
`navigator.credentials`.** Unverified for real: Safari/iOS Face ID end to end, and
`InvalidStateError` (the device is already registered). **One manual pass on an
iPhone is owed after deploy** — enrol, sign out, sign in, then try enrolling the
same device twice.

**(e) The base64url helper pair is duplicated.** `b64urlToBuffer` /
`bufferToB64url` at `frontend/js/admin.js:319`/`:328`, and
`urlBase64ToUint8Array` at `frontend/js/track.js:99`. The two files never load on
the same page so nothing is broken — but per the `invariants` skill,
`frontend/js/config.js` loads first on all eight pages and is already in `SHELL`,
so consolidating there costs **zero** new `SHELL` entries and zero script tags.
The comment above the `admin.js` pair already says this, so that comment is the
copy to delete when the move happens.

**(f) Pre-existing drift noticed but not fixed:** `docs/architecture.md` §5.6
still calls the settings attribute `operatingHours` (it is `openingHours`, owned
by `lib/opening-hours.ts` since v1.78.0), and that section does not enumerate the
settings table's other record types at all. Unrelated to this change and out of
scope for this pass — the `db-schemas` skill is authoritative and correct.

## Deploy readiness

**Nothing was committed, pushed or deployed, on explicit instruction.**

The reason is worth recording: the working tree contains substantial uncommitted
work from a **different concurrent session** — ~20 untracked files in
`backend/tests/`, plus modifications to `backend/src/expiry.ts`, `index.ts`,
`routes/pos.ts`, `routes/vouchers.ts`, `routes/checklist.ts`,
`routes/customers.ts` and `routes/push.ts`. `backend/src/routes/admin.ts` and
`backend/tests/admin-users-settings.test.ts` contain **both** that work and this
feature, so **no clean commit of only this change is possible.** That is for the
user to untangle.

When it is shipped, the order matters:

1. **`npm run deploy:backend` first.** The admin login screen calls
   `/api/auth/passkey/*`; those routes must exist before the frontend that calls
   them. Nothing here is a breaking API change — all six routes are new and every
   existing response shape is unchanged — so an old cached service-worker shell is
   unaffected and can keep working through the gap.
2. **`npm run deploy:frontend` second.**

Two things to watch:

- **The Pages workflow only triggers on pushes to `master` touching
  `frontend/**`.** This change touches both trees, so a single commit publishes
  the frontend — but if the work is split, the frontend half must be in a commit
  that touches `frontend/`, or it silently never ships.
- **`backend/package.json` and `package-lock.json` are modified** (the
  `@simplewebauthn/server` dependency). They must be committed with the backend
  change, and a deploy from a fresh checkout needs `cd backend && npm install`
  before `cdk deploy`, or esbuild has nothing to bundle.

After deploy: **do the manual iPhone pass in (d)**, and decide (a) before any
admin enrols.
