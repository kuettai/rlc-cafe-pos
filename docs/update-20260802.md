# Update — 2026-08-02

Discount precedence fix + pricing consolidation. Triggered by the question:
"what happens if Celebration mode is on and the cashier picks Newcomer?"

## Finding

Celebration mode silently cancelled the cashier's Newcomer/Pastor selection.
`createWalkUp` gated the cashier discount on `celebrationOffset > 0`, and
`approveOrder` did the same via `alreadyCelebrated`. Both dropped the
`NEWCOMER` tag entirely, so it was never persisted.

Live config at the time (`GET /api/cafe/status`): `celebrationMode: true`,
`celebrationPrice: 5`. Celebration-eligible drinks: Latte RM7, Long Black RM6,
Soda RM5.

Worked example — newcomer orders Latte + Matcha Latte:

| | Should pay | Did pay |
|---|---|---|
| Latte (eligible) | RM0 | RM5 |
| Matcha Latte (not eligible) | RM0 | RM8 |
| **Total** | **RM0** | **RM13** |

The non-eligible item was charged in full because one eligible drink in the
basket flipped the whole order to `CELEBRATION`. The more a newcomer ordered,
the more they paid.

Two secondary defects:

1. **Missing clamp.** `unitPrice` was overwritten with `celebrationPrice +
   variantModifiers` without checking it was lower, and `celebrationOffset`
   only accumulated when the delta was positive. A celebration-eligible drink
   priced below RM5 would be *raised* to RM5, and because the offset stayed 0
   the cashier-discount branch then ran against the inflated total. Not live —
   Tea (RM4) and Mineral Water (RM1) are not flagged eligible — but one click
   in Admin > Menu away.
2. **Newcomer undercount.** Three sites derived the newcomer count from
   `discountType === 'NEWCOMER'` (`pos.ts` shift summary ×2, `admin.ts`
   monthly report, feeding the end-of-day email). Every newcomer served on a
   celebration day was invisible to that metric.

Root cause of the class of bug: the pricing math existed in **four** drifted
copies — `createOrder`, `modifyOrder`, `createWalkUp`, `approveOrder`.

## Changes

**New `backend/src/lib/pricing.ts` — single source of truth.**
Discounts never stack; per line we compute every applicable price and charge
the lowest:

```
gross       = basePrice + variant modifiers
CELEBRATION = min(gross, celebrationPrice + variant modifiers)   eligible DRINKs only
STAFF       = flat RM5                                           DRINKs only
PASTOR      = RM0                                                DRINKs only
NEWCOMER    = RM0                                                DRINKs only
FOOD        = never discounted
```

Ties resolve to the cashier's explicit selection so the label identifies the
customer. `Math.min` is the clamp: a discount can never raise a price.

All four call sites now use `priceLine` + `summarizeOrderDiscount`;
`approveOrder` uses `repriceStoredItems`, which treats the stored (already
celebration-priced) `unitPrice` as the incumbent candidate, so no menu re-read
is needed.

**New fields on order records:**

| Field | Purpose |
|---|---|
| `customerClass` | Cashier's raw selection (`STAFF`/`PASTOR`/`NEWCOMER`), independent of pricing. A food-only newcomer gets no discount but is still counted. |
| `grossAmount` | Undiscounted total, for auditability. |
| `items[].grossUnitPrice` | Per-line gross, so `approveOrder` can re-apply discounts correctly. |

`isNewcomerOrder()` checks `customerClass` and falls back to `discountType`,
so historical records still count.

**Behaviour changes worth knowing:**

- Staff on a celebration day now pay the cheaper of flat RM5 and the
  celebration price (previously celebration won outright). An iced oat latte
  for staff goes RM6 → RM5.
- Ties between the cashier class and celebration now report as the cashier
  class, not `CELEBRATION`.
- Legacy `variant` strings now match on `id` **or** `name` everywhere
  (`modifyOrder` previously matched name only).
- `quantity`/`qty` are both accepted and default to 1 (`createOrder`
  previously trusted `item.quantity`).

**P2 — walk-up cart shows the real total.** `frontend/js/pricing.js` mirrors
the rule so the cashier is quoted the charged amount, with struck-out gross
and a savings line. Selecting a discount pill repaints immediately. Verified
against the backend across 336 combinations (menu × variants × class ×
celebration settings) — exact parity.

**closeCafe resets celebration mode.** It was left on with the café closed and
would have applied silently at the start of the next service. Now cleared
alongside `featuredDrinkId`.

**Hot Chocolate data fix** (`scripts/fix-hot-chocolate-variants.mjs`, applied).
The item carried a legacy `variants` entry `{name: 'Oat Milk +1',
priceModifier: 9}` on a RM8 base. Every renderer prefers `variantGroups` when
present, so it was unreachable — oat milk simply could not be ordered. Now an
optional `Milk` group at +RM1 → RM9. Verified via `GET /api/menu`.

## Security: exposed credentials and a forgeable token

Removing the test PINs from the repo surfaced something worse.

**JWT_SECRET is publicly known.** `infra/lib/infra-stack.ts:188` hardcoded
`JWT_SECRET: 'CHANGE_ME_BEFORE_DEPLOY'`, and `lambda get-function-configuration`
confirmed that is the **live value** on `rlc-cafe-api`. Anyone reading the public
repo can mint a valid ADMIN token without any PIN:

```js
jwt.sign({ userId: 'x', name: 'y', role: 'ADMIN' }, 'CHANGE_ME_BEFORE_DEPLOY')
```

`index.ts` only calls `verifyToken` and never re-reads the user record, so
nothing revokes a token short of rotating the secret. Token lifetime is 8h (the
old steering doc claimed 4h). Fixes applied:

- `lib/auth.ts` reads the secret lazily and **fails closed** — refuses to sign or
  verify when it is missing, a known placeholder, or under 32 chars. An API that
  is down beats one accepting forged admin tokens.
- `infra-stack.ts` gained `requireSecret()`, which fails **synth** unless a
  strong `JWT_SECRET` is supplied via the environment. An insecure deploy is now
  impossible rather than merely discouraged.
- ⚠️ **Rotation still outstanding** — the live value is unchanged.

**Credentials removed from the repo.** Live admin/cashier PINs were in
`.kiro/steering.md`, `docs/architecture.md`, `screenshots/README.md`,
`integration.test.ts`, both Playwright specs, and `scripts/cleanup-orders.mjs`.
All now read `TEST_ADMIN_USER`/`TEST_ADMIN_PIN` and
`TEST_CASHIER_USER`/`TEST_CASHIER_PIN` from the environment, skipping cleanly
when unset. `seed-ingredients.html` no longer prefills a valid admin userId on a
publicly served page. Note the PINs remain in git history — rotation is the only
real remediation.

**Login blocklist** (requested after the incident below). `BLOCKED_LOGIN_PATTERNS
= [/^admin/i]` plus `isBlockedIdentifier()` in `routes/auth.ts` refuses any
identifier beginning with "admin", case-insensitively, before any DB lookup, and
returns a 401 identical to a wrong-PIN response so it leaks nothing. A second
gate re-checks the resolved record's `userId`/`nameLower`/`name`. `admin.ts`
rejects creating or renaming a user to a reserved name so it cannot be
recreated. `admin-001` is deactivated in DynamoDB (`isActive: false`, with
`deactivatedAt`/`deactivatedReason`); record backed up outside the repo.

**Login auditing.** `logAuth()` in `lib/audit.ts` records every attempt —
SUCCESS / FAIL / BLOCKED_IDENTIFIER / BLOCKED_RESOLVED_USER — with source IP and
user agent, never the PIN. Before this the Lambda emitted only
START/END/REPORT, which is why the event below could not be attributed.

## Incident: integration tests were writing to production

A `admin-001` login at 15:03:27Z looked like an intruder. It was **me**.

`integration.test.ts` ran against the live API with hardcoded credentials. Its
Order Flow group per run: open the café → create a real RM7 order as
"Test Customer" → approve (deducting ingredient stock) → mark ready → close the
café, which fires `sendEndOfDaySummary`. Seven full `npm test` runs today
produced seven phantom orders, seven spurious `FEATURED_AUDIT` close rows, and
two unexplained end-of-day emails whose totals climbed 76/RM340 → 77/RM347 →
81/RM375 (RM7 per phantom).

I built an intruder narrative on a login I had caused, and only unpicked it when
the user asked why three reports disagreed. Lesson: treat "Integration Tests
(Live API)" as a production actor, and correlate anomalies against your own
actions before alarming anyone.

Remediation:

- **Double gate.** Credentials alone are insufficient; the mutating group now
  also requires `RUN_LIVE_WRITE_TESTS=1`. Verified: with credentials present but
  the flag unset, Order Flow skips and no order is created.
- **`scripts/cleanup-test-data.mjs`** removes both record types — orders
  (matching customerName AND approvedBy AND date) and `FEATURED_AUDIT` rows
  (correlated to within 15s after a test order, requiring `user=SYSTEM/CLOSE`).
  Dry run by default, backs up before deleting, aborts above 50 matches.
  The genuine 06:40:17 end-of-service close was correctly preserved.
- Cleaned: 7 orders (RM49) and 7 audit rows. Today reads 76 orders again,
  matching the real 14:41 email.
- Not reversed (accepted): ingredient stock for 7 lattes, `lastLoginAt` on
  `admin-001`, and the emails already sent.
