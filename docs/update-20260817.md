# Update — 2026-08-17

Staff ordering link (T2). A customer-facing link `?code=<CODE>` that lets a staff
member order at the staff price without queueing for the cashier to select the
class for them — drinks at the staff rate (RM5), food at full price.

## Context

Staff and pastors could only get their price through a **cashier-created walk-up
order**: the volunteer had to build the cart at the counter and pick the discount
class. On a busy Sunday that puts the slowest kind of order (someone reading the
menu at the till) in front of the queue.

T2 lets staff self-serve. The requirement that shaped the whole design: the
customer may **request** the staff price, but only the cashier may **grant** it.

## Analysis

Two decisions carried the design.

**1. A staff link is not a pre-order link.** The obvious shortcut was to reuse
`PREORDER_CODE#`. The two disagree on every axis
(`backend/src/routes/staffcode.ts:9-15`):

| | Ministry pre-order | Staff link |
|---|---|---|
| price | free, RM0 | RM5 drinks, food full price |
| status on create | PREPARING | PENDING (needs approval) |
| café-open check | bypassed | **applies** |
| food | drinks only | allowed |
| expiry | same-day ISO string | numeric TTL, plus a date gate |

So a staff order is an **ordinary** customer order — ordinary PENDING status,
ordinary numeric `expiresAt` TTL, ordinary food reservation, ordinary
PENDING→PREPARING approve — and only the pricing class differs. No new statuses,
no new transitions, no new arithmetic.

**2. A self-applied price would have stuck even when the cashier declined.** The
order has to be stored already priced at RM5 so the customer sees what they will
pay. But `repriceStoredItems` treats the stored net as the **incumbent
candidate** and only ever charges the cheaper of the two candidates
(`backend/src/lib/pricing.ts:329-346`). Approve an untouched staff-link order
without a `STAFF` selection and:

- the RM5 survives, because it is cheaper than gross; and
- it comes back out labelled `CELEBRATION`, because the incumbent net is below
  gross (`appliedRule = incumbentNet < gross ? 'CELEBRATION' : 'NONE'`).

That is a discount nobody authorised, attributed to the wrong rule, with nobody
accountable in `approvedBy` — and invisible in the discount report. This is now
recorded as a reviewable invariant (`.kiro/skills/invariants/SKILL.md`, Money):
*a customer-requested discount class must never survive approve unless the
cashier explicitly selected it.*

The fix had to restore the **no-class net**, not gross: declining a staff price
must not also throw away a legitimate celebration discount. Hence a new stored
item field rather than reusing `grossUnitPrice`.

## Changes

### Backend

- **`backend/src/routes/staffcode.ts` (new)** — staff-code storage, validation
  and the admin single-entry upsert.
  - `GET /api/staff-code/validate?code=<CODE>` — public, mirrors
    `validatePreorderCode`'s response shape so `createOrder` reads the same

## Accepted trade-off — residual security risk

Recorded here for the PR write-up. **The café accepted this knowingly; it is not
a blocker and was not treated as one.**

The staff code is permanent and guessable. It has no per-person identity, no
one-time token and no rate limit, so anyone who holds or guesses the link can
**request** the staff price — the code alphabet is deliberately small and
human-typeable, which helps a guesser as much as it helps a staff member.

The control is not the secret, it is the cashier: the price is stored as a
request, the POS forces a confirmation prompt before approve, and declining
reverts to celebration-or-full. The honest weakness is that on a busy Sunday a
volunteer may tap the primary button through without reading it.

What makes that survivable is that it is **auditable after the fact**: every
APPROVE audit line on a staff-link order records `staffCode` and
`staffPriceGranted`, so the grant rate can be reviewed and a leaked code can be
rotated or deactivated from Admin > Staff Link. Date gating (`startDate` /
`endDate`) is available if the café later wants the link to be seasonal.

# T4 — Editable ministry pre-orders (PENDING + a cashier release)

Separate work item, same working tree, same unreleased version. Pre-orders are now
**created PENDING** so the customer can still edit them, and the cashier's
PENDING → PREPARING approve — presented as **"release to barista"** — is the lock.

> Supersedes two rows of T2's comparison table above: a ministry pre-order's
> *status on create* is now **PENDING**, not PREPARING, and its expiry is an ISO
> string that can sit days out, not same-day. T2's conclusion is unaffected — a
> staff link is still not a pre-order link, and every other row still holds.

## Context — the actual harm

A pre-order was created `status: 'PREPARING'`. `modifyOrder` only edits a **PENDING**
order (`ConditionExpression: '#s = :pending'`), so a ministry pre-order was
**permanently uneditable from the moment it was placed** — days before the service
it was for. The workaround volunteers had found was to **delete the order in the
POS and ask the customer to order again**, which produced duplicate orders in the
queue and in the day's figures.

## Analysis and design

**PENDING is the whole fix.** Creating the order PENDING reuses the existing
customer *Edit Order* flow and its race-safe `#s = :pending` gate unchanged — no
new status, no new gate, no second edit path to keep in step. What was lost by
moving out of PREPARING was the implicit "the cashier owns it now" signal, so that
became explicit: the ordinary approve becomes the release, and the customer's edit
window closes exactly when the barista starts the drink.

Everything else in T4 follows from pre-orders now living in a bucket they never
lived in before, and each of these was a real hole rather than a precaution:

- **They must not be swept as stale PENDING orders.** The 1-hour cron already
  skipped `isPreOrder` defensively; that skip is now load-bearing, and is what
  lets a Wednesday pre-order survive to Sunday.
- **Closing the café must not expire them** — see below; this one was live.
- **They must still be expirable.** `expirePreOrders()` now sweeps PENDING as well
  as PREPARING/READY. Without that, an unreleased pre-order would be immortal:
  the hourly sweep skips it and `closeCafe` skips it.
- **They must not be billed at release.** `parseCustomerClass` refuses `'PREORDER'`
  from a request body and the cashier's dropdown has no such entry, so the class is
  forced from the stored `isPreOrder` flag. With a null class `repriceStoredItems`
  would keep the stored (full) `unitPrice` as the cheapest incumbent and charge the
  ministry the full gross with `discountType: 'NONE'`.
- **The edit path had to be closed as a bypass.** `modifyOrder` enforced *none* of
  the three pre-order restrictions `createOrder` enforces — drinks-only,
  `eligibleItems`, `excludedOptions`. Since a pre-order zeroes the whole gross,
  that was uncapped cost to the café: place a compliant pre-order, then edit it
  into food or into an excluded paid option. Both paths now call one helper,
  `preorderItemRejection()`. **Generalised as a new invariant:** any restriction
  enforced at create must be re-enforced on edit, or the edit endpoint *is* the
  bypass.
- **`expiresAt` stays an ISO string, and the release preserves it.** The house rule
  is "every transition out of PENDING must `REMOVE expiresAt`", and it exists
  because a *numeric* `expiresAt` is a live DynamoDB TTL. A pre-order's value is
  the ISO `serviceEndTime`: TTL only acts on numeric attributes, so it is inert,
  and it is the only input to `expirePreOrders()`. The release therefore appends
  `REMOVE expiresAt` **only when the value is not a string** — preserving the ISO
  one, stripping a stray numeric one (which would be a real armed TTL on an order
  meant to live for days).

## The bulk release

`PUT /api/pos/preorders/release-all` (CASHIER/ADMIN, no body — the acting cashier
comes from the JWT and is written to `approvedBy`) returns
`{ released, skipped, total }`. It calls the **same** helper as the per-order
release, so "release four individually" and "release all four" cannot diverge on
the guard, the pricing, the audit line, the push or the ingredient deduction.

Two safety filters, both load-bearing:

1. **`isPreOrder === true`.** The route walks *every* PENDING order, and that bucket
   is full of ordinary **unpaid** customer orders waiting for the cashier's payment
   check. Lose this filter and the route mass-approves them — unpaid orders marked
   paid and sent to the barista.
2. **Service-end date is today in Malaysia time.** A link can stay open across more
   than one service, so PENDING can hold orders for a *later* date; releasing those
   would close the edit window for customers who ordered for next week. An order
   with no usable ISO `expiresAt` is skipped and logged, never guessed at.

It also paginates on `LastEvaluatedKey`. Silent 1MB truncation in a *mutating*
batch would tell the cashier "released 40" — so they would reasonably believe the
queue was empty — while real pre-orders stayed stranded in PENDING. A per-order
`ConditionalCheckFailedException` counts as *skipped* and never fails the batch, so
`released + skipped === total` always holds.

There is deliberately **no scheduled auto-release**: a time-based release would
close the customer's edit window behind their back.

## Worth a volunteer's / maintainer's attention

1. **Closing the café previously expired every outstanding pre-order.** `closeCafe`
   queries PENDING orders **unbounded by date** and had no `isPreOrder` guard —
   it never needed one while pre-orders were born PREPARING. Under T4, closing the
   café once would have EXPIRED every pre-order for every future service. Fixed:
   `closeCafe` now skips them.
2. **Pre-order drinks now deduct ingredient stock.** `deductIngredients()` runs only
   on the approve/release path, which pre-orders never reached before (they were
   created PREPARING). Ingredient usage and stock numbers will therefore include
   pre-order drinks from now on — an accuracy improvement, but expect the figures
   to move.
3. **A live defect found and fixed en route:** in `frontend/js/track.js`,
   `isEditing` was set but **never read**, so every 7s poll re-rendered the page
   and silently threw away a customer's in-progress edit. It affects all customer
   edits, not just pre-orders. The poll now returns early while editing, and drops
   edit mode with an explanation if the order leaves PENDING (the backend would
   answer 409 anyway).

## Audit findings — T4 (follow-up pass)

An independent auditor ran 30 source mutations against the T4 tests. Most of the
suite has real teeth: the bulk-release safety filters, free-price preservation,
edit-path enforcement, ISO `expiresAt` handling, `closeCafe`, the undo round trip,
the notes prefix and the router all failed under mutation as they should. The
offline test count went **254 → 267** across two follow-up passes (14 suites).

Two findings, both new classes of bug rather than new behaviour:

1. **The most serious: the 1-hour PENDING sweep's pre-order skip was never
   exercised.** Deleting `if (order.isPreOrder === true) continue;` from
   `backend/src/expiry.ts` left all 254 tests passing. No fixture in the repo had
   ever put a row in front of *that* query — the suites staged `{ Items: [] }` for
   it, so every assertion about the sweep's behaviour was vacuous, and a
   neighbouring test appeared to cover it while staging into a different query in
   the same handler. Had that line been lost, the cron would EXPIRE every
   pre-order within an hour of creation and the `REMOVE expiresAt` on the way out
   would destroy the service-end time too: the feature dies silently, on a
   schedule, days before anyone would notice. **Now covered.**
2. **A dead branch in `approveOrder` duplicated the ISO-`expiresAt` rule.**
   `backend/src/routes/pos.ts` returns early for pre-orders and delegates to
   `releasePreOrderToPreparing()`, but the money path below still carried a full
   pre-order case — an `isPreOrder` flag always false, a `keepIsoExpiry` always
   false, and the better-written copy of the preservation comment. Unreachable,
   proven by inserting a `throw` and watching the suite stay green. The hazard was
   that the next agent could edit the no-op, verify by reading, and ship nothing.
   **Verified removed in this working tree**; what survives at the superseded site
   is a one-line pointer ("do not add a pre-order case here").

Coverage added: **`backend/tests/preorder-pending-gaps.test.ts`** (new, 13 tests,
fully mocked/offline, no credentials, writes nothing to production) — the 1-hour
sweep's pre-order skip; the `409` on a stale status for the single-order release
path; `getOrder`'s five pre-order response fields; the closed-window link still
supplying its restrictions on edit; and the admin daily-report pre-order bucket in
both directions, whose only previous coverage was the live integration suite.

Still open: **`backend/tests/pricing.test.ts` contains no `PREORDER` cases** —
confirmed, zero occurrences in the tree. The behaviour is covered elsewhere
(`preorder-pending.test.ts`), but `pricing.test.ts` is the discount *specification*
and a class that zeroes every DRINK line belongs in it. Being closed separately.

### Caveats — limits of this verification, not results

## The email root cause

`closeCafe` ended with `sendDailySummaryEmail().catch(() => {})` — started, never
awaited, fired after the handler had already returned its 200. **This was not a
config or logic fault: the summary code and the SMTP settings were correct all
along.** Lambda freezes the execution environment the instant a handler returns, so
that orphaned promise only advanced when the very same sandbox was thawed by some
later request. On busy Sundays it got that luck and the email arrived late but
intact (2026-08-02 at +50s, 2026-08-09 at +4m39s — both completing against a
*later* request id than the close). On the quiet 2026-08-16 the sandbox took two
more requests and was reaped 0.78s after the close, and no email was ever sent.
The `.catch(() => {})` swallowed the evidence, and the caller also discarded
`sendEndOfDaySummary`'s boolean return, so there was no log line either way — which
is why a missing weekly report went unnoticed for a week.

**The 2026-08-16 report is NOT recoverable by this change.** The fix is forward-only:
the next qualifying run will produce the **2026-08-23** summary. Nothing replays a
past date, and the `DAILY_SUMMARY#{date}` marker is keyed to the current MYT date.
The correct 16 August figures are not lost — they are on the **admin Reports page**,
which reads the same orders the email would have summarised. Read them there if the
number is needed.

## Why the fix is in the cron, not an `await` in `closeCafe`

Awaiting it in the handler would put a ~4s third-party SMTP call inside a cashier's
request against a 10s function timeout, on the one gesture that ends the service.
So the summary moved to the expiry cron (`sendDailySummary()` in
`backend/src/expiry.ts`), where it is awaited inside a 30s invocation, logs its
result on **every** path, and is gated three ways:

1. Malaysian **Sunday, after 2pm** — the café trades Sundays only, and this also
   stops an accidental mid-morning close from burning the day's single send on a
   partial service. The Wednesday midweek stock rule invokes the same handler, and
   the `day !== 0` gate is what stops it emailing an empty RM0 report.
2. **`cafeStatus === 'CLOSED'`** — the summary describes a finished service, so it
   waits for the cashier's Close Café rather than guessing from the clock.
3. A **`DAILY_SUMMARY#{date}`** marker (settings table, `SK=META`) written *only*
   after a confirmed send. That makes it exactly-once, and because a failure leaves
   no marker, every later run in the window retries it for free.

The EventBridge window widened from `cron(0/30 1-7 ? * SUN *)` to `1-9` (9am–5pm
MYT) so a close after 3:30pm still has a run left to carry the summary — otherwise
the fix would have reintroduced the same "no second chance" shape it removes. This
is a **CDK change, so the backend must be deployed** for it to take effect.

`closeCafe` now carries a comment block at the old call site saying explicitly that
no email belongs there, because the tempting fix is to put it back.

## The date bug, and how it survived a test

The email subject rendered a day early — "Saturday, 1 August 2026" for the 2 August
service — because `formatDate` in `backend/src/lib/email.ts` parsed midnight MYT
and then called `toLocaleDateString` with **no `timeZone` option**, so it formatted
in the runtime's zone. On Lambda that is UTC, which lands at 16:00 the previous day.
Now pinned to `Asia/Kuala_Lumpur`.

**`npm test` is now `TZ=UTC jest`.** The existing date assertion passed against the
broken code, because the dev machine's zone is already `Asia/Kuala_Lumpur` — the
ambient zone made the wrong output look right, so the test could not see the bug it
was meant to guard. Lambda is UTC; the suite now matches production.

Two traps worth recording:

- **Setting `process.env.TZ` in `setupFiles` does NOT work.** Node resolves and
  caches the process timezone before `setupFiles` runs, so the variable changes but
  `Intl.DateTimeFormat().resolvedOptions().timeZone` does not. It has to come from
  the environment *before the process starts*, which is why the pin lives in the
  `package.json` script and not in the jest config.
- **A bare `npx jest` bypasses the pin entirely.** `backend/tests/setup.ts` now
  prints a warning when the resolved zone is not UTC, and the `test-suites` skill
  was corrected — it had been recommending `npx jest --testPathIgnorePatterns
  integration`, which would have quietly undone this.

`backend/src/lib/date.ts` is new and is the single source of truth for the UTC+8
conversion (`malaysiaToday` / `malaysiaClock` / `malaysiaDayStartUtc`), extracted
from `routes/staffcode.ts`, which re-exports it so existing imports keep working.

## The root cause

`backend/src/lib/push.ts` read the VAPID keys from **Lambda environment
variables only**:

```ts
const VAPID_PUBLIC = process.env.VAPID_PUBLIC_KEY || '';
const VAPID_PRIVATE = process.env.VAPID_PRIVATE_KEY || '';
if (VAPID_PUBLIC && VAPID_PRIVATE) { webpush.setVapidDetails(...); }
```

and `infra/lib/infra-stack.ts` supplied them as
`VAPID_PUBLIC_KEY: process.env.VAPID_PUBLIC_KEY || ''`. **Any `cdk deploy` from a
shell that had not exported the keys therefore overwrote the live values with
empty strings.** There is no way to tell from the stack template that this
happened; a successful deploy is indistinguishable from one that just destroyed
the feature.

`sendOrderPush` then hit, literally:

```ts
if (!VAPID_PUBLIC || !VAPID_PRIVATE) return; // VAPID not configured, skip silently
```

No log line, ever. `GET /api/push/vapid-public-key` returned
`500 {"error":"VAPID not configured"}` in production the whole time.

## Customer impact, stated plainly

This is the part worth remembering. `frontend/js/track.js` offers a notifications
banner ("Yes, notify me"). On tap it calls `Notification.requestPermission()`
**first**, the customer **granted browser permission**, and only then did it fetch
the public key — which came back from a 500 as `undefined`, so
`pushManager.subscribe()` threw.

So the customer spent **the one notification permission they will ever grant** —
browsers do not re-prompt after a decision, and a person who has been burned once
does not go into site settings to try again — and received nothing. Not a
degraded feature: a feature that took something from the customer and gave
nothing back. That is why the "skip silently" line is now recorded as a defect in
the `invariants` skill rather than as defensive coding.

## The fix

- VAPID config moved to **SSM under `/rlc-cafe/`**: `VAPID_PUBLIC_KEY` (String —
  it is served to every browser, so it is not a secret), `VAPID_PRIVATE_KEY`
  (SecureString), `VAPID_SUBJECT` (String). `push.ts` reads it through an
  awaited, cached `ensureVapidConfigured()`; `setVapidDetails` is re-applied only
  when the public key actually changes, so a warm Lambda does no extra work per
  push. **Nothing in the deploy path can wipe an SSM parameter.**
- **The silent `return` is gone.** A missing or malformed config now
  `console.error`s, naming **which half** is missing, where it looked, and the
  `aws ssm put-parameter` command that fixes it. A config web-push actively
  *rejects* is logged separately with the subject and the key lengths — web-push
  throws at `setVapidDetails`, not at send time, so that is the only place the
  detail exists.
- `backend/src/routes/push.ts` no longer reads `process.env.VAPID_PUBLIC_KEY`. It
  goes through `ensureVapidConfigured()`, which returns a key only once web-push
  has accepted the **whole triple**. Serving a public key whose private half is
  absent would let the browser subscribe *successfully* and be undeliverable
  forever — worse than an honest 500, because it burns the permission prompt
  while looking like it worked.
- `VAPID_SUBJECT` changed from `mailto:admin@rlccafe.com` — **a domain this
  project does not own** — to `https://153.oasisofcare.org`. Push services treat
  the `sub` claim as the operator contact and may reject a bogus one.
- All three `VAPID_*` env vars **removed from the Lambda** in `infra-stack.ts`,
  with a comment saying they must not come back: the point is that there is
  nothing left for a fresh deploy shell to wipe.
- `ORIGIN_VERIFY_SECRET` no longer defaults to `CHANGE_ME_WHEN_CLOUDFRONT_ENABLED`.
  That literal is committed in a **public** repository, so the day anyone flipped
  `ENFORCE_ORIGIN_HEADER` to `'true'` the "shared secret" would have been public
  knowledge and the front-door check bypassable with one header. It is now
  `requireSecret`d when `ENFORCE_ORIGIN_HEADER === 'true'`, not emitted at all
  otherwise, and the placeholder is on the `requireSecret` denylist.

## The near-miss: a second latent copy of the same bug

Found while moving the config, and worth more than the fix that prompted it.
`getEmailConfig` called `GetParametersByPath` with **no pagination**:

```ts
const result = await ssm.send(new GetParametersByPathCommand({
  Path: SSM_PREFIX, WithDecryption: true,
}));   // no NextToken loop
```

`GetParametersByPath` returns at most **10** parameters per call. `/rlc-cafe/`
already holds **7**. Three more parameters — and this release adds three — and
`GMAIL_APP_PASSWORD` would have fallen off the first page, `getEmailConfig` would
have quietly fallen back to `process.env`, found nothing, and the end-of-day
email would have failed **in the identical indistinguishable way**: a missing
value looking exactly like a feature nobody turned on. The v1.72.0 email fix
would have been undone by arithmetic.

Both configs now share **one** paginated, 5-minute-cached fetch of the whole
prefix (`loadSsmParams`), so there is one place to get this right and one cache
to warm. The invariant is recorded as: *a paged AWS list call is paginated even
when today's count is under the page size.*

## 1 — Per-item special requests

### Backend

`backend/src/routes/orders.ts`:

- `export const ITEM_NOTE_MAX_LENGTH = 80` and
  `export function validateItemNote(raw)`, shared by `createOrder` and
  `modifyOrder`. One helper on purpose: a restriction enforced only on create
  makes the edit endpoint a bypass of it, which is the create/edit-parity class of
  bug found in v1.71 and now recorded in the `invariants` skill.
- Module-local `withItemNote()` attaches `note` to a stored item **only when
  non-empty**. So a record for an order with no item notes is **byte-identical**
  to what shipped before: no migration, no backfill, no `note: ''` sprayed across
  historical-looking items.
- Both error paths are 400 and both are raised **before any DynamoDB write**, so a
  rejected note cannot leave `foodReserved` moved:
  `'Item note must be a string'` and `'Item note cannot exceed 80 characters'`.

**Why 80 and not the per-order 200.** An item note renders one-per-line on the
barista prep card and on the POS queue card, where vertical space is the binding
constraint — a per-order note renders once, an item note renders once per line. A
four-drink order at 80 each keeps the total free text in the same order of
magnitude as a single order note. The cap is measured on the **trimmed** value, so
trailing whitespace out of a text input cannot push an otherwise-legal note over
it.

**Nothing was added to `backend/src/lib/pricing.ts`**, deliberately: a note is not
a price and affects no money. It never reaches `priceLine`,
`summarizeOrderDiscount`, `totalAmount`, `grossAmount` or `discountOffset`.

The per-order `notes` string is **kept unchanged** and still carries order-wide
requests. Only its frontend label and placeholder were repurposed, so the two
roles are unambiguous to the customer and to the cashier ("Order note:" on the
POS).

### Frontend

- **`frontend/js/app.js`** — the customer cart **no longer merges lines** by
  `id + variant`. Every drink is now its own independently-notable line at
  `qty: 1`. A one-time expansion splits legacy `localStorage` carts with
  `qty > 1` into N lines. The per-line `[−]` / `[+]` controls and the qty count
  were **removed as redundant** once every line is a single drink; the ✕ remove
  is kept. Each row gets an always-visible `maxlength="80"` note input. New
  module-level `escHtml`.

  **The user's rationale for de-merging**, recorded because it is a product
  decision and not an implementation detail: orders are mostly a single drink and
  rarely exceed four, so the cost of losing quantity controls is negligible next
  to the benefit of every drink being individually notable. A merged line cannot
  carry two different notes.

- **`frontend/js/track.js`** — the read view shows each item's note; the edit flow
  shows and edits them. **Quantity controls are deliberately kept here.** A
  *stored* order's items can legitimately have `quantity > 1` — walk-up orders and
  every historical order — and stored items are **not** de-merged. Only the
  customer cart stopped merging; the backend still handles `quantity > 1`
  everywhere.

- **`frontend/js/pos.js`** — per-item notes on the queue card, in the order detail
  and in the in-POS prep view, styled distinctly from the order-level note.
- **`frontend/prep.html`** — per-item notes for the barista.
- **`frontend/css/style.css`** — supporting styles only.

- **`frontend/js/pos-walkup.js` — unchanged, deliberately.** It renders a cart it
  builds itself and never renders a stored order's `items`, so there is no
  per-item-note render site in it. Its merge behaviour was left alone on the
  user's instruction.

## 2 — Editable pre-order collection time

No `collectionTime` attribute was added. The user decided against one, and there
still isn't one — the time continues to live only inside the
`[PRE-ORDER: CODE] Collect: …` notes prefix.

`backend/src/routes/orders.ts`:

- `export function resolveCollectionTime(preorderRecord, raw)`, shared by create
  and edit. The allowed list is the link's own `collectionOptions`, falling back
  to `DEFAULT_COLLECTION_OPTIONS` **imported from `routes/preorder.ts`**, not
  re-declared. Off-list → `400 {error:'Invalid collection time'}`; non-string →
  `400 {error:'collectionTime must be a string'}`. Matching is exact after
  trimming both sides — no case folding, no fuzzy match, because the value is
  echoed verbatim into the prefix the cashier collects against.
- A **hard-deleted link falls back to the defaults** — fail-closed. The customer
  can still change their slot, but never to free text of their own.
- **`createOrder` now validates it too.** It had accepted an arbitrary string, so
  restricting only the edit path would have been pointless: a crafted *create*
  would simply set the arbitrary value up front. This is the parity rule biting in
  the less obvious direction, and it is now written down in the `invariants`
  skill. No legitimate client is affected — the customer page only ever submits a
  value from the same list.
- **`modifyOrder`** rebuilds the prefix through the existing
  `preorderNotesPrefix` / `composePreorderNotes` / `splitPreorderNotes` helpers,
  so the format string still exists in exactly one place. The **code always comes
  from the stored order record, never the request body**, so a client can neither
  forge a code nor set an arbitrary time.
  - The `notes = :n` clause is now emitted when `body.notes !== undefined`
    **or** a validated `collectionTime` applies. This was a real defect in the
    making: a client may change nothing but the time, and the time lives *inside*
    `notes`, so under the old condition that request would have written nothing at
    all.
  - When `body.notes` is absent the stored customer portion is preserved verbatim
    rather than blanked while the prefix is rewritten around it.
  - A validated time **creates** the prefix on a pre-order that had none — one

## 3 — Escaping: a live XSS in the cashier's authenticated session

Found while adding the note render sites. **Every site below was verified against
the committed code before anything was changed**, and one claim that reached this
pass was a false positive.

- **`frontend/prep.html` escaped nothing at all.** `${i.name}`, `${i.variant}`,
  `${o.customerName}` and `${o.notes}` were raw interpolations into `innerHTML`.
  The order-level `notes` is **customer-typed free text**, so this was a live
  injection path onto the barista's screen. An inline `esc()` covering all five of
  `& < > " '` now wraps every order/item/customer interpolation on the page,
  including the pre-existing ones. Inline is the right call there: the page has a
  self-contained script and loads only `js/config.js`.

- **`frontend/js/pos.js`** had raw `customerName`, `items[].name`,
  `items[].variant` and `notes` on the queue card, in the order detail and in the
  in-POS prep view. The POS session holds a **CASHIER JWT in `sessionStorage`**,
  so script injected there runs with till privileges — this was
  privilege-bearing, not cosmetic. All of them now go through the
  **already-existing** `escapeHtmlPos`, which escapes all five characters and so
  is safe in a quoted attribute as well as in text.

- **The shape of the bug is the lesson.** The same `customerName` field was
  *already escaped* in the v1.71 dialogs (`askStaffPrice`,
  `confirmReleaseNotToday`) and unescaped on the card behind them. The newer code
  got it right; the v1.0 hot path was never revisited. Escaping is a property of
  the **render site**, not of the field — recorded as a new invariant.

- **False positive, deliberately not changed.** `pos.js` builds a cancellation
  string from a raw `customerName` and passes it to `showCancelToast`, which
  assigns **`textContent`**. That is a safe sink; escaping first would show the
  cashier a literal `&quot;`. Same for `showNameFlash`. Both verified in the file
  and left alone. The counterpart rule — *a `textContent` sink must not be
  escaped* — is recorded alongside the main one, specifically to stop the next
  agent over-correcting.
