# Update 2026-10-22

Shipped as **v1.84.0** (minor — user-visible feature).

## Asked for

1. Admin-defined sort sequence for ingredients, honoured by POS → Stock Count.
2. A "Low Stock" subfilter on Admin → Setup → Ingredients.

## Changes

- **`sortOrder` on `INGREDIENT#…/META`** (number | null). Set from the
  ingredient form; blank sends `null` (not 0 — 0 is a real position). `POST
  /api/admin/ingredients` stores it only when it is a finite number. The generic
  `PUT /api/admin/ingredients/{id}` already accepted arbitrary fields, so no
  route change there.
- **`compareIngredientsForCount`** (`backend/src/routes/pos.ts`) — one
  comparator for both `GET /api/pos/ingredients` (stock count) and
  `GET /api/pos/inventory` (admin list): sortOrder ascending, unordered rows
  after every ordered one, then the existing location rule (unlocated last,
  explicit null handling — no sentinel), then name. `sortOrder` added to the slim
  stock-count projection.
- **Low Stock subfilter** (`frontend/js/admin-ingredients.js`) — toggle that
  narrows the current location filter; uses the same rule as the Low Stock
  badge (`isIngredientLow`: active and `currentStock <= lowStockThreshold`).

## Verification

- `npx tsc` clean; `npm test` 44 suites, 2174 passed. New tests: 4 sortOrder
  ordering cases in `pos-inventory-menu.test.ts`, 1 create case in
  `admin-catalog.test.ts`.
- Fixture browser probe of the admin page (`serviceWorkers:'block'`, every API
  call stubbed, 0 requests reached production): filter combinations, count
  label, edit-form round trip (`sortOrder: null` on blank) all correct.

## Open items

- Existing ingredients have no `sortOrder`, so order is unchanged until an admin
  numbers them. Numbers span all locations — use ranges per location to keep
  them grouped.

# v1.85.0 — drag-and-drop Rearrange (same day)

## Asked for

Reorder ingredients on the Ingredients page itself instead of editing each
Sort Order one by one. No live-save per drop: a "Rearrange" button next to
"+ Add Ingredient" enters a mode with Edit/Delete/toggle disabled, and Save
confirms.

## Changes

- **`PUT /api/admin/ingredients/reorder`** (`routes/admin.ts`) — body
  `{ order: [ingredientId…] }`, 1–500 unique non-empty ids ≤ 64 chars, else 400
  and no writes. Sets `sortOrder = position (1-based)`. Each `UpdateCommand`
  carries `ConditionExpression: attribute_exists(PK)` — an Update on an absent
  key CREATES the item, so a stale/forged id would otherwise leave a
  sortOrder-only phantom ingredient. Those ids are returned in `missing`.
  Routed before the generic `/{id}` PUT (which would treat "reorder" as an id).
  Behind the existing ADMIN gate in `index.ts`.
- **Rearrange mode** (`frontend/js/admin-ingredients.js`) — working order in
  `ingRearrange`; whole list (filters hidden); drag via pointer events on the
  ⠿ handle (HTML5 DnD does not work on touch) plus ↑/↓ buttons that keep focus;
  `#n` labels preview the position Save will write. A card only moves within
  its group (active / disabled) because disabled rows always render last.
- **Mobile card layout** (`frontend/css/admin.css`) — `.admin-ing-row` wraps the
  actions onto their own line ≤ 899px, mirroring `.admin-menu-row`. Pre-existing
  defect: names and subtitles were crushed to one word per line on phones.

## Found while testing

- First drag implementation listened on the handle with `setPointerCapture`.
  Moving the card re-parents the handle, which releases capture, so the drag
  stopped after the first swap. Now listens on `document`.
- `hidden` attribute lost to an inline `display:flex`; the probe checked the
  property, not the computed style. Both fixed.

## Verification

- `npm test` 44 suites, 2186 passed (13 new reorder-route tests).
- Fixture browser probe at 1024×768, 768×1024, 390×844 (`serviceWorkers:'block'`,
  every API call stubbed, 0 requests escaped): mouse drag, CDP touch drag,
  disabled-row drag rejected, ↑/↓ with focus retained, controls disabled,
  Save body, return to normal mode. Screenshots reviewed.
- The `admin.html:55` "addEventListener of undefined" page error is a probe
  artifact (SW registration under `serviceWorkers:'block'`), present on the
  untouched baseline.
