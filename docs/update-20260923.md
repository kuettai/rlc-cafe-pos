# Update 2026-09-23

Release pass for **v1.80.0 — TV display fullscreen layout + slideshow
cross-fade, and one service-worker fix.**

**Frontend-only.** No `backend/`, no `infra/`, no schema change, so
`npm run deploy:backend` is not part of this release. Only
`npm run deploy:frontend` ships it.

## Context

Three changes to the TV display board (`display.html` — the 1080p screen in the
café foyer) and its service worker were built and approved earlier in the
session. This pass is the release work: version bump, changelog, documentation
and skill sync, verification, commit and push.

The visual work was mocked first and approved before any real CSS was touched
(`tmp/display-fullscreen-mock.html`, scratch — deliberately **not** shipped).

## Analysis

### 1. `frontend/sw.js` — non-`http(s)` requests were being cached

The `fetch` listener ran every request through one of three branches, and two of
them write to the cache. A browser extension on the display machine was issuing
`chrome-extension://` fetches, which the service worker intercepts like any
other; `cache.put` **rejects** on a scheme the Cache API does not support, which
rejects the `respondWith` promise and fails a request the page never made.

The fix is one guard as the first line of the handler:

```js
if (!e.request.url.startsWith('http')) return;
```

Returning *without* calling `respondWith` is the important part — it hands the
request back to the browser's default handling, which is the only correct answer
for a scheme we do not cache.

### 2. `frontend/js/display.js` + `display.css` — the cross-fade was not a cross-fade

The old slideshow had a single `<img id="promoImg">`. `showSlide()` added a
`.fade-out` class, then a `setTimeout(…, 1000)` hard-coded to match a `1s` CSS
transition swapped `src` and removed the class. Two consequences, both visible on
a large screen:

- the fade went **through the dark `#111` panel background** between every slide,
  rather than one image dissolving into the next;
- the new `src` only began decoding *as it became visible*, so the fade-in could
  reveal a partially decoded image.

Plus the timer and the CSS duration were two numbers in two files that had to
agree, with nothing to catch a change to one of them.

Now: two stacked `.promo-layer` images (`promoImgA` / `promoImgB`), both
`position:absolute; inset:0`, transitioning **`opacity` only** (1.2s), with
`.active` as the visible state. `showSlide()` preloads the incoming URL through a
throwaway `new Image()` and performs the class swap in its `onload` / `onerror`,
so the overlap happens between two fully decoded frames.

The old CSS-selector fallback rules (`img[src=""] ~ .display-promo-fallback` and
friends) are gone — with two layers those selectors cannot express the state. The
branding fallback is now JS-driven, and `clearPromoLayers()` is the single reset
path; previously two separate branches in `fetchSlides()` each cleared one `src`
by hand.

### 3. `frontend/display.html` + `display.css` — fullscreen image, overlaid orders

`.display-container` was a `grid-template-columns:2fr 1fr` split: photo on the
left, orders in a flat navy column on the right. On the foyer TV that spent a
third of the screen on at most 13 order numbers and cropped every photo to two
thirds width.

Now `.display-container` is `position:relative`, `.display-promo` sits at
`inset:0`, and `.display-orders` is absolutely positioned over the right 30%
(`min-width:380px`, `z-index:10`).

Because the orders now sit over an arbitrary photograph rather than a flat
background, readability is carried by a **horizontal scrim** on the panel
(transparent → `rgba(10,14,26,0.35)` at 18% → `rgba(10,14,26,0.92)`), plus
`backdrop-filter:blur(2px)` and `text-shadow` on the hero cards, compact items,
dividers and empty state. Hero-card fills went from opaque to
`rgba(6,95,70,0.85)` and their glow shadow from green to black, so the card reads
as sitting *on* the photo.

Portrait TV mounts (the `@media (orientation:portrait)` block) previously
restacked the grid 60%/40%. They now get the same overlay treatment as a bottom
strip: `inset:auto 0 0 0`, `height:42%`, scrim rotated to `to top`.

**Graceful degradation checked:** every blurred surface also carries an opaque-
enough `rgba` fill and, on the compact items, a `1px` border — so a TV browser
without `backdrop-filter` support loses the blur and keeps the contrast.

### Not part of this diff: a production data change

Three `DISPLAY_SLIDE#…/META` records in `rlc-cafe-settings` had aged out
(`expiryDate` in the past), leaving the display with nothing to show. Their
`expiryDate` was moved to `2026-12-31` earlier in the session with
`scripts/bump-slide-expiry.mjs`, **already run against production**. Recorded
here for the audit trail; there is nothing to re-run and nothing user-visible to
add to the changelog.

The script conforms to the `Data scripts` invariants: dry run by default, writes
only with `--apply`, prints a before/after diff, idempotent, region
`ap-southeast-5` hardcoded. It touches `expiryDate` only and its header says why
it must never touch `expiresAt` — the settings table's TTL fires on that
attribute, so a numeric value on a slide would have DynamoDB delete it silently.
That distinction is now also in the `db-schemas` skill, where it was missing.

# Part 2 — v1.81.0: display-slide editing

Second release pass of the same day, and a **separate feature** from v1.80.0
above. v1.80.0 was the TV board's own layout (`display.html`); this is the admin
screen that manages the slides feeding it (`admin-display.js` +
`backend/src/routes/admin.ts`). They share a subject and nothing else, which is
why they got two versions, two changelog entries and two commits rather than one.

**Backend + frontend.** Unlike v1.80.0, `npm run deploy:backend` is part of this
release and had to run **first** — see Deploy below.

This pass closes open item (d) of Part 1: the work was deliberately left
uncommitted there rather than shipped half-way.

## Context

Adding a slide was possible; changing one was not. Correcting a typo in a title,
or shifting an expiry date by a week, meant deleting the slide and re-uploading
the image through the whole presign flow. The feature was implemented and tested
by an earlier agent in this session; this pass is the release work — verification,
version, changelog, doc/skill sync, deploy.

One decision was escalated during implementation and is recorded here because it
is a **behaviour change to an already-shipped endpoint**, not a new-code-only
change. Asked whether to harden create as well as edit, or edit only, the user
chose **harden both**. Rationale, and why it is the right call: the
`YYYY-MM-DD` + `expiry >= start` rule had lived *only* in the browser form, so
`POST /api/admin/display/slides` already accepted a free-text date and an
inverted range from any direct caller. Hardening only the new edit route would
have been theatre — a crafted create sets the bad value up front. So the shared
validator runs on both, and the POST now returns `400` for input it used to
store.

## Analysis

### 1. `slideDateRejection()` — one validator, both write paths

`backend/src/routes/admin.ts:53`, called from `:1178` (create) and `:1207`
(edit). Returns the rejection sentence or `null`. Three checks: both dates
present and strings, both matching `/^\d{4}-\d{2}-\d{2}$/`, and
`expiryDate >= startDate` (equal is a valid one-day window).

The format check is load-bearing rather than cosmetic. `routes/display.ts:67`
selects today's slides with a **lexicographic string compare**
(`s.startDate <= today && s.expiryDate >= today`). A value like `'16/08/2026'`
is therefore never *rejected* downstream — it is silently **mis-compared**
(`'16/…'` sorts after `'2026-…'`), and the slide simply never appears on the
foyer TV, with nothing logged anywhere. An inverted range is the same class of
silent failure: a slide that can be shown on no date at all. The string compare
in `display.ts` is only safe *because* the write paths now guarantee the shape.

### 2. The edit route's two deliberate restrictions

`PUT /api/admin/display/slides/{id}`, ADMIN-only via the router's `/api/admin`
prefix gate.

- **`imageUrl` is not editable.** The `UpdateExpression` is a fixed four-field
  allowlist (`title`, `startDate`, `expiryDate`, `sortOrder`), never built by
  iterating the request body — which is simultaneously what keeps `PK`, `SK`,
  `slideId` and `createdAt` unreachable. Replacing an image stays delete +
  re-upload. The edit form reflects this: it shows the image read-only with a
  one-line explanation, and no file input, because a control that cannot do
  anything is worse than its absence.
- **`ConditionExpression: attribute_exists(PK)`.** A DynamoDB `UpdateCommand`
  upserts by default. Without the guard, a PUT to an already-deleted `slideId`
  writes a **new partial record with no `imageUrl`**, which the display page
  renders as a broken image on a 1080p screen in the foyer. The
  `ConditionalCheckFailedException` is mapped to `404 {error:'Slide not found'}`.

### 3. A test that had pinned the defect in place

`backend/tests/admin-misc.test.ts` carried
`it('does NOT validate the date FORMAT, nor that expiry follows start')`,
asserting `201` for both a free-text date and an inverted range. Its comment
described the resulting production failure accurately and at length — and still
asserted the broken behaviour was expected, so adding the validator turned the
suite red. Rewritten as three positive tests (format rejected, inverted range
rejected, `start === expiry` accepted), each also asserting **no write
happened**. This is the second instance of this pattern in the repo, so it went
into `invariants` as a named hazard rather than a one-off note: a
characterisation test that *understands* the danger is still a test that fails
when the danger is fixed.

## Deploy

**Order was load-bearing and is the whole reason this did not ship with v1.80.0.**
The frontend Edit button calls an endpoint that only exists after the Lambda
deploy, and the Pages workflow triggers on any push touching `frontend/**`:

1. `npm run deploy:backend` — CDK → `ap-southeast-5`, account `956288449190`.
   Must be confirmed complete before step 2.
2. `npm run deploy:frontend` — commit + push to `master`; Actions publishes Pages.

Reversing these would put a live Edit button in front of an old Lambda — a `404`
on every save, for however long the backend deploy takes.

**Status at the time of writing: prepared but NOT deployed, and NOT committed.**
Both commands are left for the user to run, in the order above. The live-API
check of the Edit button is therefore also still outstanding — the `PUT` route
has never existed in production, so nothing has exercised it end to end yet; the
evidence so far is the unit/dispatch suite and a static review, not a real
request.

The `POST` behaviour change ships with the backend, so between the two steps the
API was briefly stricter than the still-cached create form required. That is
harmless in this direction: the old form already enforced the same two rules
client-side, so no input it would have submitted is newly rejected.
