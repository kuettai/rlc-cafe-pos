## Context

The customer page's closed screen was three hardcoded lines that said the café
opens at 10:15 and 12:45 on Sundays. The schedule was a literal in
`frontend/js/app.js`, repeated in the admin bundle, and disagreed with two other
notions of the same thing elsewhere in the repo. A customer arriving on a Sunday
was told nothing useful about *when*, and nobody could change the times without a
deploy.

Two things came out of it: a real backend module that owns the schedule, and an
admin editor for it. A pre-existing repo-wide test bug was found and fixed on the
way, and it invalidates every test count previously written down for this repo.

## Analysis

**The schedule existed in five disagreeing places.** Three hardcoded frontend
strings (now gone), plus two that are still live and were deliberately not
rewired — see follow-ups (a) and (b). `/api/admin/reports/sessions` buckets orders
by **8:00–14:00 MYT** while the dashboard cards over that very data are captioned
`Session 1 (10:15-11:30)` / `Session 2 (12:45-13:30)`. So the heading and the
numbers beneath it disagree **today**, before any of this work.

**Why the decision has to be server-side.** `00:30 on a Sunday in MYT is still
Saturday in UTC`, so a UTC-derived day-of-week reports "not a service day" for the
eight hours before 08:00 MYT on the one day the café actually opens. That is the
same fault that headed the 2026-08-02 and 2026-08-09 end-of-day summary emails
"Saturday". Made in `lib/opening-hours.ts` beside `lib/date.ts`, it is testable
under `TZ=UTC jest` with an injected clock; made in a browser it is not.

**A phase bug that only a "who reads this field?" question would find.** The first
cut validated, normalised and persisted `closesAt` while `describeOpeningState`
keyed **only** off `opensAt`. The field was not merely unused — the phases actively
**lied**: at 10:20, five minutes into session 1, `phase` read `BETWEEN_SESSIONS`;
at 13:29, inside session 2, it read `AFTER_LAST_TODAY`. Customer-visible
consequence: the closed screen told a congregant standing there at **10:20 on a
Sunday** that the café opens at **12:45** — a 2.5-hour wait — because the
volunteers were five minutes late unlocking the counter. A mistyped `closesAt`
would have been undetectable by any test, since the value had no observable effect
anywhere. Fixed by the `WITHIN_SESSION` phase, now the only reader of `closesAt`.
Generalised into an invariant.

**A repo-wide test bug: CI was silently losing a whole suite.** Eleven files in
`backend/tests/` had no top-level `import`/`export`, so ts-jest compiled them as
**global scripts** whose top-level `const`s redeclared each other (`TS2451` on
`mockDbSend`, `handleOrders`, `LATTE`). The diagnostic appears **only on a cold
cache**, so every warm local run looked green while a clean CI checkout dropped a
file — and the victim moves with compile order (it was `daily-summary.test.ts`,
−7 tests; after two unrelated files were added it moved to
`preorder-excluded-options.test.ts`). **Every test count reported for this repo
before today was a warm-cache number.**

**A checkable claim in the `invariants` skill was false.** It justified five copies
of the HTML escaper with "there is no shared frontend util module and adding one
costs a new `SHELL` entry plus a script tag on every page".
**`frontend/js/config.js` is that module**: verified as the *first*
`<script src="js/config.js">` on **all eight** HTML pages and already present in
the `sw.js` `SHELL` array. A shared frontend helper therefore costs **zero** new
SHELL entries and zero new script tags. The cost used to justify the duplication
does not exist. (The escapers may stay — they are audited — but that reason may not
be cited again.) The claim is repeated in two code comments, follow-up (g).

### One correction made in this pass

**The claim "the `+08:00` literal now appears exactly once in the backend" is
false**, and it had propagated into four places: the `invariants` skill, the
`project.md` layout block, the `feature-history.md` entry, and the `lib/date.ts`

four of them **outside** `lib/date.ts`.

| Site | Form | Verdict |
|---|---|---|
| `lib/date.ts:59` | `` `${dateIso}T${hhmm}:00+08:00` `` | canonical |
| `lib/email.ts:194` (`formatDate`) | `dateStr + 'T00:00:00+08:00'` | **a straight duplicate of `malaysiaDayStartUtc(dateStr)`** — and this is the very function whose date bug produced the "Saturday" subject lines |
| `routes/receipt.ts:103`, `:155`, `:174` | `dateStr + '+08:00'` | interpreting a timezone-less bank-receipt timestamp; a defensible distinct case, still three hardcoded copies |

Plus two non-literal offset copies outside `lib/date.ts`: `routes/preorder.ts:108`
(`+ 8 * 60 * 60 * 1000`) and `routes/admin.ts:481`/`:498` (`(utcHour + 8) % 24`).
**Eight offset sites in `backend/src/`, one of which is the source of truth.**

What is true — and what the docs now say — is that **`lib/date.ts` owns the
conversion, and `malaysiaTimeUtc` is the one place *inside it* that writes the
